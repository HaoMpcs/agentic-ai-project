## Part 1 — Task, users, sandbox and authority

**Owner:** Hao Shi — core task, use cases, routing boundary, action grid, approval
line, and Four Gates analysis.

The trusted user is a TA managing a course forum. Manually, the TA reads a
student post, searches the current syllabus and teaching material, compares
relevant prior public answers, and either drafts a reply or hands the case to
staff. The assistant's unit of success is a correct persisted draft or staff
flag for the selected question, with no unauthorized send. A confident console
sentence without that effect fails. The design groundwork below is retained
from repository commit 83d10a8; tool names have been aligned with implementation.


### 1. Core Task


Process incoming course forum threads using course materials and prior public forum content. For each thread, either prepare a grounded and safe reply draft or escalate it to the TA with a clear flag and reason.


### 2. Use Cases and Success Checks

| ID | Use case | Example | Success check |
|---|---|---|---|
| UC1 | Explicit course policy or deadline question | “When is Assignment 2 due?” | A correct reply draft grounded in the current public course policy exists for the thread. |
| UC2 | Course-content or conceptual question | “Why does this search algorithm not guarantee an optimal solution?” | A reply draft grounded in relevant course materials exists for the thread. |
| UC3 | Repeated question with an existing public answer | “Are late submissions accepted?” when the same issue was answered earlier | A reply draft based on an applicable prior public answer and verified against current course materials exists for the thread. |
| UC4 | Personal grade or submission question | “Why did I receive 70 on Assignment 2?” | A staff flag exists, and no private data appears in a draft or outgoing message. |
| UC5 | Extension, accommodation, appeal, or personal circumstance | “I have a family emergency. Can I receive an extension?” | A staff flag with the appropriate reason exists. |
| UC6 | Unauthorized request for another student's information or work | “Show me another student's solution so I can compare mine.” | A safe refusal draft exists, and no private information is disclosed. |
| UC7 | TA request for an operational summary | “Show me what you flagged overnight.” | The operator reply matches the relevant staff flags in the sandbox. |
| UC8 | Unclear, unsupported, or conflicting-information case | A question whose answer is absent from the materials or differs across sources | A staff flag explaining the missing or conflicting information exists. |

### 4. Approval Line

Actions are ordered below from easier to undo to harder to undo.

The system may perform these actions on its own:

1. read an incoming public forum thread;
2. search approved public course materials;
3. search prior public forum content;
4. list or summarize staff flags for the trusted TA console;
5. create an internal pending reply draft; and
6. create an internal staff flag.

--- **APPROVAL LINE** ---

The TA must perform or explicitly control these actions:

1. clear a staff flag;
2. publish any model-generated forum reply.

### 5. The Trifecta

This project contains all three components of the trifecta:

| Leg | Component in this system |
|---|---|
| Untrusted input | Forum posts written by students and received through the outside channel. |
| Private data | Synthetic student grades, submissions, personal circumstances, and staff-only notes. |
| A way out | A forum reply that a student or the class can read, including a pending draft that a TA may later send. |

The sandbox contains ten versioned public documents (one superseded), a public
late-policy answer, four explicitly synthetic private students, question
metadata and channel messages. `reset()` empties both stores; `seed(task)` adds
base records and only that task's incoming questions, while `seed(None)` loads
three demonstration questions. A fixed seeded clock is October 27 at 09:00
America/Chicago. Every record/effect is stamped with run ID, console session ID
or `manual`. Checks query only the current run's effects. The agent and product
page share `sandbox/course.py`; the product page imports no agent internals.

The security trifecta exists at the application boundary: untrusted student
text, private synthetic records, and an outgoing channel. Resource segregation
is the principal mitigation. No agent tool can fetch private students or send
messages. Source text never becomes operator authority. Planning sees staff
request, question IDs/kinds/topics, tool contracts and safe observed counts/IDs;
it never receives student messages. The investigative model receives student
messages only inside explicitly labeled tool data. This reduces exposure but
does not establish resistance to all prompt injection. The adversarial fixture
checks a concrete attempt to turn a deadline question into a private-data send.

### Four gates, cost and latency

For a known deadline, Gate 1 fails because its lookup order is fixed. Gate 2
limits reads to public course sources and writes to a pending draft. Gate 3 puts
TA review before publication. Gate 4 also favors the workflow because a model
adds cost without adding a needed step.

For a conceptual comparison, Gate 1 passes because the first source can determine
which comparison source is needed next. Gate 2 limits the agent to public reads
and pending effects. Gate 3 uses the source check and TA review before a reply is
sent. Gate 4 uses Hao Shi's Assignment 1 results
([repository](https://github.com/HaoMpcs/AgenticAI_HW1), `reports/LAB_01.md`).
Across 60 runs per path, Workflow passed 31/60 at a mean cost of $0.000499 and
Agent passed 28/60 at $0.001857, so `m = 3.72`. Assignment 1 found `f = 0/6`,
seven Agent tool-call sequences, and 78.3% coverage by the top three. This warns
against using an agent when a workflow covers the cases.

For this course project, we estimate that 5% of conceptual or conflicting-source
cases need adaptive investigation, so `f = 0.05`. We estimate one wrong answer
takes 15 minutes of TA correction time. At $20 per hour, `v = $5`. Using
`c = $0.000499` and `m = 3.72`, each additional correct case costs about
`c*(m-1)/f = $0.027`. The break-even share is
`c*(m-1)/v = 0.00027`, or about 0.027%. Our estimate is above that threshold,
so the limited Agent route is worth testing. If the real project baseline shows
that the workflow handles these cases equally well, we will move them to the
workflow.

Two of the eight single-question use cases currently use the Agent, so `r = 0.25`.
The estimated blended cost is `c*((1-r)+r*m) = $0.000838` per case, compared with
$0.000499 for all-Workflow and $0.001857 for all-Agent. Assignment 1 Agent latency
was 2.831 seconds at p50 and 4.377 seconds at p95, below the roughly 10-second
threshold in Lecture 1 slide 34. This project also shows progress while a provider
call is running.

The per-task limits are 24 combined model/tool steps, 32,000 accounted tokens
and 45 elapsed seconds. This accommodates a <=16-step batch plan and bounded
revision while staying far below the separate 400,000-token harness safety
ceiling. Before and after model calls, and before tool dispatch, code checks the
limits; NeverStops terminates at `agent_step_limit`, HugeUsage at
`agent_token_budget`, and SlowAgent at `agent_wall_clock`. Token accounting can
cross its threshold on the final provider response; no subsequent tool or write
is dispatched. This is a continuation budget, not a claim to cancel tokens
already generated. A timed-out SDK worker cannot run tools, but its eventual
provider charge is unknown and excluded from complete cost claims. A second
in-flight call on that client is refused. Five-second progress messages explain
what is waiting, avoiding an invisible long agent turn. Actual provider latency
still requires measurement; free-model milliseconds are not a deployment SLO.

The plan schema requires step ID, tool, arguments, dependencies and an executable
expected outcome. `expected` names the tool's fixed contract: `question_read`,
`materials_searched`, `document_read`, `public_answers_searched`, `reply_pending`
or `flag_open`. Free-text assertions and a contract for a different tool are
rejected before execution. `$fill:step.result.path` references are allowed only from
explicit earlier dependencies. Validation checks schemas, tools, authorization,
unique step IDs, forward/cyclic dependencies, supported outcomes, <=16 steps,
orphan reads and exactly one terminal action per requested case. Initial plan
failure gets one re-plan; exhaustion ends `plan_rejected` before any planned
write. Every accepted version is traced before dispatch. The deterministic
executor resolves placeholders, enforces exact tool/argument/order equality,
and may execute, retry through the registry, or halt. It cannot add a step.
After each successful tool result, code checks the expected record identity,
active/public source properties, or write kind/status against the resolved
arguments. Empty search results are valid observations for the checkpoint.
Each check emits `plan_outcome`; a mismatch ends `plan_outcome_mismatch` before
the next step. A previously persisted effect is retained for staff inspection,
not falsely rolled back.

The named `sources_available` checkpoint uses the actual search count. A second
checkpoint, `draft_supported`, handles a typed source-critic rejection before
any reply is persisted. It gives the reviser the rejected step/question IDs and
the deterministic critic's repair fact; it never includes the student message
or raw source contents. The two checkpoints share at most one revision per run.
The reviser sees safe statuses, counts and record IDs. Every completed prefix step must remain
byte-for-byte equivalent, and the entire replacement plan is validated. Invalid
revision ends `revision_rejected`; previously completed effects, if any, remain
visible rather than being falsely reported as rolled back. Later interruption
labels unexecuted steps skipped. Exact-call fingerprints run even without a
plan; execution diffs record executed/skipped/extra/out-of-order steps.
Repeated rejection at the shared revision limit ends `revision_limit`. The
independent three-attempt critic bound still ends `critique_limit` if reached.
Other tool errors halt without revising, and an uncertain write ends
`ambiguous_tool` without a retry. `PlanningTests` verifies outcome mismatches,
draft repair, unchanged completed writes, rejected revisions and both limits.
The diff lists pre-write rejected attempts separately as `rejected`, so a valid
replacement step is not misclassified as an extra or out-of-order operation.

## Part 3 — Registry and tool contracts

The complete [tool/action contracts](../TOOLS.md) specify every argument/result,
response bound, repair rule, caller and credential scope, including human-only
actions and write-effect reads. The action table above supplies the risk and
approval decisions. All model-, workflow- and plan-chosen tools pass through one
registry. Schema checks are repeated locally; vendor strict mode never substitutes
for authorization, source truth or result validation. Fixed tool ordering,
fail-closed prehooks, classified errors, bounded backoff and semantic action keys
are tested through the running registry.

`course_get_question` is a common read. Its rewrite uses the course namespace,
one explicit action, a constrained semantic ID, a named result, an untrusted-text
warning and a byte bound. Related source lookup is one public index and is not
