Objectives of this milestone
Your team carries on from Milestone 1's build, each switch at its verdict, and makes it hold up. Part 1 makes it survive a crash, a wait for a stranger's reply, a long session and the operator's next session (Lecture 4). It also finishes Lecture 3's work: writes, the MCP server, and a tool list that does not crowd the window. And it builds Lecture 2's context work. Part 2 puts it under rules a person sets and the model cannot change, with approvals, an escalation and a stop that work from the app, and tells the strangers it writes to that an agent wrote it (Lecture 5). Part 3 decides with Lecture 6's gates whether it is one agent or several, and builds the split on a branch. Part 4 runs at least two passes of the improvement loop on The Project page, each from a problem you saw. Every design is yours. There is no new starter: you build on your own repository as Milestone 1 left it. You may reuse your own Assignment 2 to 6 code, and the course code your assignments shipped with, naming each in CHANGES.md.

As in Milestone 1, your project's problem decides where each part is needed, and your decision table keeps every answer. These are decided where they apply, each shown one of each way, a place where it helps, which you build, and one where it does not, which you leave out, argued by the lecture's test: a checkpoint, per step with a side effect; code that calls the tools, per use case; deferred loading, by the size of your tool list; asking the stranger, per use case; notes and compaction, per kind of session; memory, per kind of fact; the column each action class sits in; approval at the plan or per action, per use case with a plan; each escalation signal, per use case; and a second agent, per component. Some things you build in every place, with no decision to make: the three exits on every write whose outcome is unknown, irreversible steps last, the recovery test, the MCP server, every call assembled within a budget, provenance on every memory record, the policy enforced in the registry's hook, an approval screen of facts your code computed, the queue page, the stop with its three commands, messages sent mid-task, and a line on every message to a stranger saying an agent wrote it. Three are built even where the test says no, behind a switch set by it, so that a pass can turn them on: deferred loading, code that calls the tools (on the use case closest to needing it, if none does), and the second agent (on a branch).

The write-up becomes your report's section 2 (state and topology) and its section 4 (the autonomy model), and adds the MCP server to its section 3; the passes join the ledger. Slide numbers in Part 1 are Lecture 4's, in Part 2 Lecture 5's and in Part 3 Lecture 6's, unless the text names another lecture; Part 4 always names it.

Part 1 · State, the outside exchange and memory (Lecture 4)
Description
Lecture 4 separated three questions that get mixed up: what carries within a run, what carries between runs, and what survives a crash. "The three have different fixes and no fix crosses between them" (slide 6). This part builds all three: context within a long session, checkpoints and a wait that survive a crash and a restart, and a memory the operator's next session reads. It also finishes Lecture 3's work on writes (what to do when you cannot tell whether a write happened, and which write goes last), serves your tools over MCP, and keeps the tool list from crowding the window.

Start from Assignments 2 and 4. Cite a member's Assignment 4 results for what the tracker held when the process was killed at every step, with the keys and with them broken, and for the boundary each lost fact crossed and the fix that brought it back; and Assignment 2's for notes against compaction: whose repository, which numbers, what they showed. Code you reuse from them gets tests here.
The app in this milestone adds the threads page's waits, console sessions that survive a restart (make serve serves the app without resetting the sandbox), and, from Part 2, the approvals and queue pages and the stop.
Tests on a fake model, as in Milestone 1: the starter's scripted models or a fake of your own, marked free = True. Some tests here stop a process and carry on in a new one, or send a message while a turn runs, which run.py cannot do: it gives every run a new ID and a fresh sandbox, and plays each turn after the last one returns, handing the scripted strangers' answers and approvals to the run before the operator's next turn. Write those as tests in tests/, with fixed_run and check_run from tests/support.py (the starter's README.md, "Testing on a fake model"): each process the test starts opens the run under the same run ID, the first one seeding the test task, and calls harness.turns itself; check_run then runs the test task's check. A message mid-turn comes from a second thread.
Every switch this milestone adds carries added: with its date, on the switch itself, since runs already exist in results/ (Milestone 1, Part 1, task 5). A switch whose setting is a plain value, such as a number, takes the long form so that it can carry the date: context_budget: {setting: 16000, added: <date>}.
Tasks
The durability boundary (slides 6 and 7). Take what your system knows, such as the operator's task, the plan and each step's status, a stranger's reply, and what the operator said last week, and say what must carry within a run, between runs and across a crash, and what carries each. What must outlive the run belongs in a store or a checkpoint, never only in the context window (slide 30). Then draw your system: its components, the registry and the MCP server (task 3), your data, state, memory and control flow, the app and the runner calling the agent's one entry point, and the operator console and the outside channel as two separate ways in. On it, draw the durability boundary as three zones: what survives a crash; what outlives the run into the next session; what lives only in the context window. Keep it as Mermaid, or an image with an editable source: the final submission draws its trust boundaries on it.

Checkpoints, and writes whose outcome is unknown. Resuming replays everything since the last checkpoint, so a write in that stretch happens again unless something stops it (slide 10).

Each step marked (slide 13), on each path: a read (safe to repeat), a keyed write (safe: the target returns the first result) or an unkeyed write (it happens again).
Where a checkpoint helps (slides 11 and 13), per step with a side effect: would replaying the step repeat an effect no key closes? Then a checkpoint before it, or move the step last. A keyed write needs none when its arguments are fixed before it runs (a workflow's step, a plan's step); on the agent loop the model writes them, and may write others on a replay, which gives a new key and a second effect, so save the call, its arguments included, before it runs. Add one after a read too costly to repeat. Show one of each: a step that needs a checkpoint and one that does not, each argued; each write's answer goes on its action's row in the decision table. The replay window runs from the last checkpoint to the step running at the crash, that step included. Assignment 4 put one before every write.
The durability mode (slide 12), per kind of run: exit saves only when the run ends (it finishes, fails or pauses for a person), and a crash loses the whole run; async saves after every step in the background, and a crash in the gap loses that step too; sync saves after every step before the next one starts, slowest and safest. The mode is set per run: sync for any run with an irreversible step, async or exit for runs that only read. The modes save after every step; your system saves where your placement puts a checkpoint, and the mode says how each of those saves is written. Give each kind of run's mode, a run whose only writes are keyed and reversible included, such as a refund run or a run that only answers the operator, with its reason.
What a checkpoint holds (slide 14): the plan as validated, where there is one; each step's status; the completed calls with their keys and results; the findings so far; the current step. The conversation is optional: a chat needs it, trimmed, and a task resumes from these fields. A console session is a chat, so say whether its runs' checkpoints keep the conversation and, if they do, how much of it. Everything serializes: no open files or connections. Checkpoints are keyed by the run, on a durable backend (a SQLite file will do): in a run.py run, its run ID; in the app, where one console session holds many runs (several cases waiting at once, a fresh run after a replaced task), the session plus a run number your code gives each run. The same key names the run's wait, stop flag and hold. Checkpoints hold one run's state and are not your memory store (slide 9). state/ is reset before every run.py run and is not committed, so when a run ends, write its last checkpoint into its trace (trace.event): the final submission re-executes a failing session from one.
Coordinators decide; steps act (slide 15): the coordinator (your workflow code, or the agent loop) decides the next step, and your code resumes the run; each step does its side effect under its key and is retried on its own, so recovery happens step by step, without rerunning the agent loop. Recovery never depends on the model remembering where it was.
The resume: replay from the last checkpoint; skip a step whose key is among the completed calls, or reuse its recorded result; replay a write with the arguments the checkpoint saved, never new ones from the model. Nothing resumes a run at start-up on its own: a run resumes when a call reaches it (the operator's next turn, a stranger's reply, an approval). Say which call resumes each kind of waiting run, and what resumes a run the crash stopped.
The three exits (Lecture 3, slide 40), for every write whose call failed or timed out, the step running at a crash included: read whether the effect happened. Yes: carry on with the existing result. No: retry under the same key. Cannot tell: escalate, and say to whom (Part 2, task 5; until it is built, the run ends with a reason you name and the operator is told). Your tool table's ambiguous errors take this route.
Irreversible steps last (Lecture 3, slide 41). When a step fails after others have succeeded, retry it if its failure is temporary; otherwise compensate the completed steps in reverse order, where a compensation exists. Order each plan and each workflow so that its irreversible steps come last, or say why one cannot.
The recovery test, in tests/. Like Assignment 4's --die-during-step, it kills the process with kill -9 after the sandbox commits a write and before your system records it, then resumes in a new process under the same ID. On every test task that makes a write, kill it during its last write: the check passes, the sandbox holds one effect per intended write, and the resume repeated no completed call. A fake model will do. For each write you crashed, keep what the sandbox held before the run, after the crash and after the resume, and add the last to Milestone 1's "Did the effect happen?" table.
Serve the tools over MCP (Lecture 3, slides 45 to 47). Since its stateless revision, an MCP server keeps nothing between requests: no handshake and no session (Lecture 3, slide 45). A broken stream loses the request in flight, and carrying identifiers from one call to the next becomes the model's job (Lecture 3, slide 46). Your registry stays in your own code and calls the server's tools, so its validation, keys, call record and hook hold for every call. Build the server to Lecture 3, slide 47's rules:

Every call carries the IDs it needs, and every result returns the IDs the next call needs (the thread, the record, the next page), semantic so that they survive compaction.
Every write carries its key, added by the registry, never seen or written by the model; the server, or the target behind it, accepts each key once.
State between calls lives in your own code, in the call record and the checkpoint: not in the server, and not only in the model's context.
tools/list returns the tools in the same order every time (Lecture 3, slide 28).
An execution error comes back in the result with isError: true, and a protocol error as a JSON-RPC error (Lecture 3, slide 34); the registry routes each as in Milestone 1.
Strict mode, as sent (Lecture 3, slides 20 and 21). Send one request carrying every tool your decision table makes strict, with the definitions as the registry sends them, and keep your vendor's answer: it accepts them, or names what it refuses. If your vendor has no strict mode, say so.
Add your MCP SDK to requirements.txt. The registry starts the server itself, as a child process or in its own process, so make app and run.py need nothing more.

If your SDK lags the revision, name it, its version and the revision it implements, with the date you checked. If it still opens a session or sends initialize, design as if it did not: keep nothing in the session that a call needs, and use none of Roots, Sampling or Logging, which the revision deprecated.

Part 2 · Autonomy, approvals and the stop (Lecture 5)
Description
Milestone 1 drew your approval line, kept every action below it out of the agent's tools, and left it to the operator by hand.
